## 1. 项目背景与目标

### 1.1 业务背景（原文）

> 「某高校保卫处与学生会联合运营失物招领服务，八个园区门卫室每月收到失物数百件。原来靠纸质登记本加微信群发布：挂失信息与拾物信息对不上，校园卡与耳机这类物品被反复询问，认领时仅凭口述特征就交付，交付后台账迟迟不更新，出现过误领与重复上缴。保卫处希望上线失物招领与认领核验系统，把失物登记、检索、认领申请、特征核验与物品交接纳入系统，并让热门检索与列表页在缓存层与库表保持一致。本系统考核点不同：只做失物检索缓存的失效与一致性，不做门禁刷卡与监控视频的接入检索。」
> —— 任务书 P1 §2

- **涉及数据记录**：物品记录、类别字典（结构**原文未说明**）、缓存键。

### 2.4 FR-04 ★ 失物列表与检索缓存一致性维护（核心考核点，单独深入分析）

- **原始编号**：FR-04（原文带 ★ 标记，为核心考核点）
- **来源**：任务书 P2 §4（第 4 条）；并见 P1 §1、P1 §3-3、P2 §6-1、P3 §7 AC-04、P3 §11、P4 §12
- **原文**：「FR-04 ★ 失物列表与检索缓存一致性维护：写操作一律先提交数据库再删除受影响缓存键，键按查询条件维度设计；缓存剔除或过期后检索结果必须与库表逐条一致（差异数为 0）；注入缓存删除失败时，补偿任务须在 1 分钟内修复，期间已认领物品不得继续出现在待认领列表；每次失效与修复均须留痕。」

#### 2.4.1 原文可拆出的子规则

| 子编号 | 子规则（原文语义） | 原文依据 |
| --- | --- | --- |
| FR-04a | 写操作**一律**先提交数据库，**再**删除受影响缓存键（顺序被锁定，不可颠倒） | P2 §4 FR-04；P2 §6-1「缓存只允许由服务端在事务提交后失效」 |
| FR-04b | 缓存键**按查询条件维度**设计（具体维度原文未列举） | P2 §4 FR-04 |
| FR-04c | 缓存剔除或过期后，检索结果与库表**逐条一致**，**差异数为 0** | P2 §4 FR-04；P3 AC-04 |
| FR-04d | 注入缓存删除失败时，**补偿任务须在 1 分钟内修复** | P2 §4 FR-04；P3 AC-04 |
| FR-04e | 上述 1 分钟（或整个失效窗口）**期间，已认领物品不得继续出现在待认领列表** | P2 §4 FR-04；P3 AC-04；P1 §3-3 |
| FR-04f | 每次**失效与修复均须留痕**，且留痕须含**键名、操作者与前后值** | P2 §4 FR-04；P2 §6-1 |

#### 2.4.2 深度分析（只分析，不选方案）

1. **写后失效（Cache-Aside 写路径）被原文锁定**：顺序为「DB 提交 → 删除缓存」。原文同时锁定「缓存只允许由服务端在事务提交后失效，禁止前端触发写缓存」。
   - 遗留歧义：**未命中回填（read-through/write-back-on-read）是否允许、由谁触发**，原文只禁止「前端触发写缓存」；服务端回填是否允许需确认（Q-B-02、Q-C-06）。
2. **「键按查询条件维度设计」**：查询条件维度原文明确列举的有 地点、时间、类别、关键词（FR-02），可能还包括分页、排序、下钻层级。**键的粒度（粗粒度单键 vs 条件组合键 vs 版本号/命名空间）原文未规定**，而这正是本题「不可交给 AI」的判断之一（P4 §12-3 明确举例「缓存键粒度」）。
3. **「差异数为 0」的比对口径**：逐条比对的对象是「检索结果集」还是「待认领列表」？比对是全量键还是抽样键？比对时机（每次写操作后 / 定时任务 / 验收时）原文未说明（Q-C-06）。
4. **1 分钟修复窗口与「已认领不得出现在待认领列表」的张力**：若缓存删除失败且旧值仍可命中，则在最长 1 分钟内，已认领物品可能仍出现在待认领列表。原文同时要求「1 分钟内修复」与「期间不得出现」，**这意味着需要某种机制在修复完成前避免陈旧命中**（例如读时二次校验数据库、缩短 TTL、版本号校验、删除失败即降级直查）。**原文未指定用哪种机制**，属 B 类技术实现选择（B-03）；但「期间不得出现」是否允许最长 60 秒内的短暂陈旧、如何判定「出现陈旧列表」，属**验收口径**，须向老师确认（C-19）。P4 §12-3 也把「陈旧窗口可接受范围」列为不可交给 AI 的判断。
5. **留痕字段**：键名、操作者、前后值。其中「前后值」在删除场景下的含义（被删的缓存内容？被删的键对应版本？）原文未说明（Q-C-06）。
6. **与 FR-03 的关系**：热榜由缓存提供且「可核对」，是否同样纳入 FR-04 的一致性范围，原文未明说（Q-C-06）。

#### 2.4.3 测试场景（计划，非已执行结果）

- 正常：
  - 〔原文〕N1：写操作（登记/修改/状态流转）后，受影响键被删除，下一次读取为库表最新值；
  - 〔推导〕N2：多维度查询键（地点/时间/类别/关键词/组合）逐一验证失效覆盖完整（由「键按查询条件维度设计」推出，维度集合待 C-06 确认）；
  - 〔原文〕N3：缓存剔除后检索结果与库表逐条一致（差异数 0）；
  - 〔原文〕N4：缓存自然过期后检索结果与库表逐条一致；
  - 〔原文〕N5：失效与修复留痕记录完整（键名、操作者、前后值）。
- 异常/负向：
  - 〔原文〕E1：**注入**缓存删除失败，补偿任务在 1 分钟内完成修复；
  - 〔原文〕E2：注入失败期间，已认领物品不出现在待认领列表（AC-04 判定线）；
  - 〔原文〕E3：Redis 完全不可用时，登记不被阻断（NFR-03），检索直查库；
  - 〔建议〕E4：补偿任务重复执行幂等，不产生错误前后值（原文未要求补偿任务幂等，属工程建议）；
  - 〔建议〕E5：并发写同一物品时，不出现「后写被先失效覆盖」导致的永久陈旧——**并发时序与并发正确性要求原文未说明**（B-17）。
- **对应验收标准**：AC-04（主判定）、AC-06（性能不得因一致性机制破坏）、AC-03（状态变更引发的列表变化）。
